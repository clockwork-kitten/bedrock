# Task #10: Rule: no arrow functions

## What was built
Implemented the `no-arrow-functions` rule for Bedrock.js with:
- **TransformPass** (`arrowToFunctionExpression`): mechanically rewrites all arrow functions to `function` expressions. Infers name from variable declarator context. Preserves `async` modifier.
- **ViolationPass** (`detectDefaultParams`): flags default parameters (too context-dependent to auto-fix).
- **ViolationPass** (`detectAsyncNoAwait`): flags async functions that contain no `await` expression.

## Key decisions made
- `j.functionExpression()` constructor ignores the `async` parameter (5th arg), so we set `fn.async = arrow.async` manually after construction.
- Expression-body arrows generate multi-line output from jscodeshift (new BlockStatement with ReturnStatement), so fixtures reflect that.
- Block-body arrows preserve their original single-line formatting via jscodeshift's reuse behavior, so the block-body fixture output is single-line.
- `functionHasAwait` checks only the `BlockStatement` body (not expression bodies) to satisfy TypeScript type narrowing.
- Used a local `NodeWithLoc` type for the `locOf` helper to avoid `jscodeshift.ASTNode` not having `.loc` on all variants.

## Issues encountered
- `j.functionExpression(..., async)` doesn't set `async` — had to assign `fn.async` manually after creation.
- `jscodeshift.ASTNode` doesn't have `.loc` on all union variants (e.g. `EnumBooleanBody`) — used a local `NodeWithLoc` type.
- `j(node.body)` where `node` is `jscodeshift.Function` requires narrowing to `BlockStatement` first for TS to accept it.
- Fixture output formats required trial-and-error to match jscodeshift's actual codegen (block-body stays single-line, expression-body becomes multi-line).
